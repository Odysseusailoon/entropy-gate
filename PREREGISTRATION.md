# Net-benefit protocol v3

Primary question: At the same ordinary-model answer-distribution estimation error, does entropy allocation reduce total algorithmic FLOPs and GPU occupied seconds after all method-specific costs? Primary attribution comparison: entropy versus uniform within the same shared-prefix framework.

## Population, frozen design and estimator

The formal study uses Qwen/Qwen3-8B on five H200 GPUs. Qwen/Qwen3-1.7B on A100 is for engineering debugging only, using development questions. Its timings, calibration, reference and outcomes cannot substitute for or be pooled into the formal study. The formal model is Qwen/Qwen3-8B, non-thinking, temperature=1, top_p=1, top_k=-1, min_p=0. Eight fixed GSM8K train demonstrations (indices 0–7), exact rendered chat template and prompt token IDs. Model/tokenizer/dataset revisions are immutable SHA commits. Development: train indices 8–17. Held-out test: test indices 1000–1049. Any additional prior tuning IDs must be declared; overlap is rejected. Gate configuration, parsing, termination, sampler numerics, batching, cost definitions, epsilon thresholds and code are frozen before calibration.

Four methods: ordinary IID full rollout; shared prefix + uniform; shared prefix + entropy; Arithmetic Sampling. Every run pays one prompt prefill and reuses that prompt KV. Every path has standard autoregressive KV caching. Forks reuse generated-prefix KV values with private writable cache assembly. Same dtype, attention implementation, maximum batch, stable batching order and active-row removal rules across methods. No cross-run prompt cache: every independent run begins cold and pays exactly one prefill.

Each fork run generates R=8 independent prefixes to generated position 64 or EOS, whichever comes first. R is fixed before sampling. The decision uses only full-vocabulary entropy on those already generated prefix positions. Entropy units: bits. Distributions include all special-token probability mass; positions whose drawn token is special are excluded from the gate's mean. Uniform computes no unnecessary entropy. beta=1 and n_min=1. Hamilton rounding preserves total child count. A parent of mass w splits into k children of mass w/k, with no change to token distributions. No forced replacements or proposal intervention. Each complete run has unit mass. Completed EOS parents retain their mass without model continuation. No pilot future or reference answer can enter allocation. New continuations use independent domain-separated RNG streams. Uniform and entropy share root/child random streams within a paired test block.

Estimator: P_hat(y)=(1/R) sum_r (1/k_r) sum_j 1[Y_rj=y]. Conditional on sampled prefixes and chosen counts, each continuation has the original conditional distribution. Taking expectation over independent prefixes yields the original marginal outcome distribution. Fixed R can create a variance floor; a favorable result is not assumed.

Answer extraction reads only the last Final answer: marker, with exact rational number normalization. Invalid retains its probability mass. The ordinary target is generation to EOS. The current formal 8B/H200 configuration uses a 1024-token emergency guard. The 1.7B/A100 debug profile uses 4096 tokens; this debug setting does not amend the formal configuration. If the formal development preflight exposes censoring, revise the guard and establish a fresh matching protocol and reference before testing. A maximum-token guard is an emergency censoring event, never treated as EOS; default allowed censoring rate is zero. Invalid must remain below 5%.

## Arithmetic Sampling implementation

Implement Algorithm 1 and Definition 3 of [Vilnis et al., ICML 2023](https://proceedings.mlr.press/v202/vilnis23a.html): shared random shift U, c_i=(i/(N+1)+U) mod 1, i=1..N; invert the original-model token CDF; map the selected interval affinely back to [0,1); continue to EOS. Equal sample weights within one dependent arithmetic run. Independent shifts across independent runs. No top-k filters, deduplication, independent code refresh per token, or substitution with stochastic beam search.

As in the [authors' code](https://github.com/google-research/google-research/blob/master/arithmetic_sampling/t5x/decoding.py), use a common random vocabulary permutation per generated position, reproducible across batches. CDF accumulation and normalization use float64 for both IID and Arithmetic. Residual codes use exact rational updates on those CDF intervals to prevent precision exhaustion on long paths. Initial shared shift has B=(maximum_tokens+1)*ceil(log2(vocab_size))+128 bits. The finite-shift discretization over the bounded sequence space is negligible at this precision; this does not remove floating-point model/CDF numerical error. Boundary rounding of float proxies is corrected against exact codes. All CPU integer arithmetic and synchronization time is charged. This is a faithful algorithm port with a different numerical implementation, not a reproduction of the authors' T5X throughput.

## Development calibration and fixed test work

IID anchors: 16,32,64 complete paths; 10 independent test runs per configuration/question. Development candidates: 8,16,32,48,64,96,128 paths/leaves, 3 independent runs on each development question. Select method-specific sample counts by nearest mean development total FLOPs to IID anchors, with a frozen maximum relative calibration gap of 35%. Include method-specific development/warmup amortization over the declared test run count. Gate parameters, roots and prefix depth are not selected from test outcomes. If the candidate range is insufficient, establish a new protocol before any test execution; no extrapolation or test-time count adjustment.

Seal all selected sample counts and development cost provenance before test jobs can be initialized. Testing finishes all predetermined paths regardless of their observed lengths or outcomes. No completion-only filtering at a wall-time limit; no discard of expensive completed samples; no adaptive test stopping. Report observed costs and mismatches to developmental budget targets, without asserting exact realized budget equality.

## Cost accounting

FLOPs: executed tensor-operator/shape census across prompt/prefix/continuation model calls, entropy, CDF, gate and weighted answer aggregation. FMA=2; scalar arithmetic and exp/log/pow/rsqrt/trigonometric primitives follow explicitly frozen per-operator formulas. Fused attention is expanded mathematically, including QK, scale, softmax, AV. This is a conventional operator FLOP count, not a physical instruction counter or a bare 2*N*token estimate. Unknown floating-point operators stop scoring. Counts and non-FLOP operator coverage are archived.

RNG, indexing/comparison/sorting, exact-integer/rational arithmetic, allocation, memory movement and KV copies are outside that floating-point convention but inside the timing interval. GPU seconds are synchronized wall time while one GPU is occupied by the complete algorithm: before paid prompt prefill through final weighted answer histogram. Include Python dispatch, CPU gate work, sampling, parser, cache copies and synchronization. This is not a sum of kernel busy times.

BF16 batch-size changes can alter rounding and consequently sampled paths. Require strict same-seed token/weight/allocation replay within the SAME configured batching regime. Cross-batch whole-path equality is diagnostic only. Separately probe next-token probabilities on identical fixed development prefixes (generated positions 1, 16, 64 when available), comparing batch=1 with the configured maximum batch. Maximum row total variation must be at most .01; this is a local numerical check, not a bound on full answer-distribution bias. RNG stream indexing is independently checked with exact synthetic tests.

Time the uninstrumented algorithm first. Replay identical seeds with the census for FLOPs, verifying identical token IDs, weights, branch allocations and execution shape. Archive instrumentation time separately; profiler overhead is measurement infrastructure and must not distort algorithm timing. Primary net cost adds all method-specific development calibration runs and discarded worker warmups, amortized over Q*B*R declared test runs for that method. Also report inference-only costs. Warmups from every actual test worker invocation are added in final analysis. Common model loading, correctness preflight, independent reference and instrumentation are experimental infrastructure outside estimator net cost, with the scope stated in the report. Do not selectively omit method-specific pilot or exploration work.

## Queue, reference and replication units

The formal study uses one SQLite queue on one node and five homogeneous H200 workers. GPU admission is read-only and rejects occupied devices. The launcher never evicts external processes. A test/calibration task is one complete matched question/configuration/run block with a randomized order of four methods, all on the same GPU. Reference tasks are independent IID chunks interleaved in the same test queue. Worker identity/hardware are archived. Failed blocks halt the queue. Crash recovery is explicit, does not use rollout duration as a selection criterion, and preserves worker/GPU affinity for partially completed paired blocks. Completed results are immutable checksummed checkpoints.

Reuse sealed v3 independent references only if exact target/prompt/numerical environment and raw checksums match; source seeds must be independent. Start otherwise with 1024 IID samples per question. Test convergence with JS(P512,P1024); if unstable, extend all questions via predeclared independent sample doublings to 2048 or 4096 without rerunning test methods. Mean half-vs-full JS threshold: 0.01 bits, plus invalid/censoring gates. Reference is sealed only when accepted; gate cannot access its outcomes. This is a high-budget approximation, not mathematical truth.

## Outputs, confidence intervals and decisions

Primary error: Jensen–Shannon divergence in bits, not its square-root distance. Also report squared L2. Errors are macro averages over questions and independent runs against the frozen reference. Costs are total cohort costs averaged over independent runs. Two figures only: observed total FLOPs vs JS, and observed GPU seconds vs JS. Plot raw frozen operating points and intervals; connecting lines are visual guides, never common-cost interpolation or extrapolation.

Frozen JS epsilon values: .01,.02,.05. At each epsilon, cost is the minimum cost among OBSERVED configurations whose mean JS meets the threshold. Report speedup for each individual baseline and for the best baseline among observed configurations: baseline_cost / entropy_cost. Unreached thresholds stay unreached. No interpolation, forced monotonicity or outcome-selected extra budget grid.

Paired hierarchical bootstrap: resample questions, then complete independent runs within each selected question/configuration. Use identical indices for all methods and cost/error metrics. Never bootstrap leaves as independent observations. Reselect the best baseline inside each bootstrap draw. Record how often both sides reach epsilon; if fewer than 95% do, suppress the numeric CI and report inadequate threshold coverage. Confidence intervals condition on the frozen reference and calibration, not their sampling uncertainty. The primary entropy-vs-uniform comparison must be reported even if entropy beats IID.

Expansion is supported only with demonstrated improvement over IID and uniform on both FLOPs and GPU seconds; report performance against Arithmetic/best baseline too. FLOP-only improvement calls for implementation optimization. IID-only improvement cannot be attributed to entropy. No improvement or insufficient threshold coverage does not establish intrinsic entropy-signal usefulness and does not justify automatic expansion. Synthetic/CPU validation never supports GPU speedup claims.
